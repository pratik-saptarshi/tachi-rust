Tachi-Rust CI Improvement Plan

This plan integrates the CI comparison between rocinante and tachi-rust into an execution-ready roadmap. The goal is to reduce wasted CI runtime on pull requests, preserve strong governance and SARIF-grade reporting, and add release-aware fan-out without weakening current security or cross-platform guarantees.

Non-Negotiables Keep SARIF, keep path-specific contract lanes, keep cross-platform checks

Executive Judgement

Adopt Add a ci-scope style router, release-vs-delta execution, workflow parse checks, and explicit timeout discipline.
Do Not Copy Blindly Do not reuse rocinante's extension-based path rules as-is; they would under-test workspace-level changes in tachi-rust.
Preserve Keep tachi-rust's stronger SARIF, supply-chain, and path-filtered contract workflows as baseline policy.

Integration stance: merge orchestration improvements from rocinante into tachi-rust while retaining tachi-rust's stronger lint, security, and specialized gate posture.

Phase 1: Fast-Fail Baseline

Objective: fail broken workflow syntax and formatting drift before expensive workspace builds start.

  1. Create a dedicated workflow-parse job using actionlint.
  2. Create a dedicated formatting workflow using cargo fmt --check.
  3. Add concurrency to PR-facing workflows to cancel obsolete runs.
  4. Standardize a short, visible bootstrap summary so failures are obvious in the Actions graph.

Deliverables

  • .github/workflows/ci-workflow-parse.yml or equivalent parse lane.
  • .github/workflows/rust-fmt.yml or equivalent formatting lane.
  • Branch concurrency groups across PR-heavy workflows.

Acceptance Criteria

  • A malformed workflow expression fails in under 90 seconds without invoking full Rust test matrices.
  • A formatting-only regression fails in an isolated lane with no dependency on package test execution.
  • Superseded PR pushes cancel earlier in-flight runs on the same ref.

Phase 2: Repo-Aware Delta Routing

Objective: replace always-on full PR fan-out with impacted execution that understands workspace semantics instead of using generic file extensions.

Design Rules

  • Treat Cargo.lock, workspace Cargo.toml, shared scripts, and workflow files as full-fan-out triggers.
  • Treat crate-local source changes as impacted-package triggers.
  • Treat specialized contract-surface changes as triggers for their existing path-filtered workflows, not for unrelated full matrices.
  • Docs-only PRs should still run cheap governance lanes, but not the full Rust workspace test graph.

Implementation Tasks

  1. Add a routing job that computes changed files from PR base/head or push before/after SHA.
  2. Map changed paths to impacted crates and to specialized workflows.
  3. Expose router outputs as workflow outputs consumed by Rust test, lint, and canary lanes.
  4. Document fallback behavior: if routing data is incomplete, default to safe full execution.

Acceptance Criteria

  • A docs-only PR does not run the full package matrix.
  • A change isolated to one crate runs only the impacted package set plus required shared gates.
  • A lockfile or shared-manifest change forces full Rust validation.
  • Fallback mode is explicit in logs and fails safe to broader coverage, never narrower coverage.

Phase 3: Preserve Specialized Governance

Objective: integrate delta routing without breaking the workflows that already encode domain-specific contracts.

Must Preserve

  • Cross-platform init compatibility matrix.
  • Fresh-install mmdc preflight contract.
  • Gitleaks SARIF upload.
  • Rust clippy SARIF upload.
  • Supply-chain audit and deny policy.
  • Feature/coverage canary schedule.

Plan Tasks

  • Define which workflows remain standalone and why.
  • Add comments to prevent future "merge everything into one CI file" drift.
  • Ensure new router outputs do not bypass specialized path filters.
  • Document ownership boundaries between core CI and specialist gates.

Acceptance Criteria

  • All existing specialist workflows still trigger on their contract surface after refactoring.
  • No SARIF-producing workflow loses upload behavior or security-events permissions.
  • No cross-platform portability workflow is collapsed into Linux-only CI.

Phase 4: Shared Setup and Cost Reduction

Objective: cut maintenance drag without erasing diagnostic separation.

  1. Extract repeated Rust setup, cache, and diagnostic steps into a composite action or reusable workflow.
  2. Keep per-lane commands isolated so failures still point to one responsibility.
  3. Standardize timeout values and lane-level duration notices.
  4. Record per-lane timing in job summaries to make future optimization evidence-based.

Acceptance Criteria

  • Shared setup logic is defined once and consumed by PR-facing Rust workflows.
  • Each heavy lane emits elapsed runtime in logs or summaries.
  • Setup refactor does not reduce failure localization.

Phase 5: Release and Mainline Policy

Objective: ensure the optimization only narrows PR cost, not release confidence.

  • On main and release refs, run full Rust workspace validation regardless of delta analysis.
  • Keep scheduled canaries, supply-chain lanes, and security lanes independent from PR routing logic.
  • Prefer explicit "full" mode names in logs so operators know when the safe path is in force.

Acceptance Criteria

  • Release/mainline execution is equal to or broader than current validation breadth.
  • No delta optimization suppresses required release coverage, supply-chain, or security lanes.
  • Operators can identify full-mode versus delta-mode from the workflow summary alone.

S.M.A.R.T. Acceptance Criteria

  1. Specific: Introduce delta-aware PR CI that narrows execution by impact while retaining full execution on main, release refs, lockfile changes, shared manifests, and workflow changes.
  2. Measurable: Reduce median PR CI wall-clock for docs-only and crate-local changes by at least 35% compared with the pre-router baseline across the first 10 successful PR runs after rollout.
  3. Measurable: Ensure 100% of malformed workflow changes fail in the dedicated parse lane before full Rust test matrices start.
  4. Achievable: Deliver Phase 1 and Phase 2 without removing existing SARIF, supply-chain, mmdc, or cross-platform workflows.
  5. Relevant: Preserve security, governance, and portability signals while cutting unnecessary PR compute and reviewer wait time.
  6. Time-Bound: Complete Phases 1-3 within 7 calendar days, Phase 4 within 10 calendar days, and Phase 5 validation by the next mainline release candidate.

Exact Adoption Order

  1. P0.1: Add concurrency to PR-facing workflows. This is the lowest-risk compute reduction and does not change test semantics.
  2. P0.2: Add ci-workflow-parse. Fail broken workflow edits before any topology refactor begins.
  3. P0.3: Add isolated cargo fmt --check workflow. Remove formatting drift from the expensive Rust path.
  4. P0.4: Introduce router logic in read-only mode first. Emit mode and impacted targets in logs, but do not yet narrow execution.
  5. P0.5: Turn on router-controlled narrowing for docs-only and crate-local PRs with full-mode fallback for lockfiles, manifests, workflows, and shared scripts.
  6. P1.1: Update rust-workspace.yml to consume router outputs and split execution by impacted package group rather than unconditional full matrix.
  7. P1.2: Freeze and document specialist workflows as protected lanes: init matrix, mmdc preflight, clippy SARIF, supply-chain, and gitleaks.
  8. P1.3: Extract repeated setup, cache, and proof steps into a shared composite action or reusable workflow.
  9. P2.1: Review overlap between core Rust CI and dedicated clippy workflow, then decide whether duplicate lint execution should stay for visibility or be reduced for cost.
  10. P2.2: Add timing summaries and baseline reporting after the routing model is stable.
Why This Order The sequence front-loads cheap, low-risk guardrails, then adds observability, then changes routing semantics, and only after that refactors shared setup.
Ordering Constraint Do not narrow PR execution before router logs prove the classification is correct across docs-only, crate-local, workflow, and lockfile change sets.
